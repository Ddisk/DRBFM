01 / 全体の構成

使う流れと、育てる流れをつなぐ

元資料を正式な記録として保管し、検索しやすく整理したナレッジをCopilotが参照する。生成した内容は、人が判断してから業務に使う。

資料を登録してAIを再学習するのではなく、回答時に根拠を検索・参照する。
修正内容は会話だけに残さず、正式な台帳へ反映する。
01
02 / 質問と回答

結論が変わる情報から質問する

利用者の入力例シャフト径を小さくしたい。
Copilotの質問例どの部分を、何mmから何mmへ変更しますか？
伝達トルクや材質も変更しますか？
利用者の回答例軸端部をφ14からφ12へ。トルクと材質は同じ。
次の確認例キー・軸受・相手部品の取付部も変更範囲に含まれますか？

会話は架空の例。実際の影響判断には対象構造・寸法・使用条件が必要。

質問のルール

  • 入力済みの情報は聞かない。
  • 影響判断に重要な順に１〜３問ずつ聞く。
  • 不明なら「未確認」で進める。
  • 条件が変われば結論も変わることを示す。

出力のルール

  • 影響・理由・適用条件をセットにする。
  • 根拠の事例IDと出典を示す。
  • 関連する変更の要否を提示する。
  • 分からないことは断定しない。
出力の区分扱い
過去資料に記載過去の条件と記録を示す。今回も同じ結果になるとは限らない。
今回への推定共通点・相違点と推定理由を示す。
確認観点からの候補過去実績とは区別し、確認が必要な事項として示す。
02
03 / ナレッジ辞書

３つの知識を、役割ごとに整理する

種類記録する内容目的
用語辞書正式名称・略称・同義語・意味・適用範囲表記ゆれを吸収する。
事例集対象・変更点・影響・条件・結果・出典過去の検討を根拠にする。
確認観点表変更分類・確認項目・質問・適用条件類似事例だけでは拾えない観点を補う。

用語の例

「軸」「シャフト」を同義語候補として登録する。

部門や製品で意味が異なる略称は、適用範囲を残して区別する。

確認観点の例

材質変更：質量、剛性、熱膨張、防錆、加工、調達。

すべての変更に影響があると断定せず、対象に応じて確認する。

「事実」「推定」「一般的な確認観点」を混ぜない。
同義語の追加や確認観点の修正にも、理由・更新日・確認者を残す。

この３区分は情報の設計上の分類。実際に３つの別リストへ分けるかは、利用するエージェントの参照先制限を確認して決める。

04 / 台帳の設計

１行に、１つの変更と１つの影響

同じ変更に影響が３つある場合は３行に分け、共通の変更IDで関連付ける。セル結合や「同上」を避け、各行だけでも意味が分かる形にする。

情報のまとまり項目
識別事例ID、変更ID、対象製品・部品、変更分類
変更内容変更前、変更後、変更の目的・範囲
影響内容影響項目、影響の説明、理由、適用条件
確認結果想定／計算確認／試験確認など、確認した条件・結果
出典資料ID、資料の版、ファイルへのリンク、シート名、行・セル位置
管理情報台帳の版、更新日、確認者、修正理由、登録状態、使用中／廃止
「影響なし」「記載なし」「未確認」は別の意味。
空欄を「問題なし」と解釈しない。「問題なし」も確認した条件とセットで残す。

登録状態（候補／確認済み）と、検証状況（想定／計算済み／試験済み）は別に管理する。確認済みの台帳にも、未検証の懸念事項は存在する。

05 / 新資料の取り込み

フォルダに追加し、差分を確認して登録

同じ様式のExcelを所定の場所へ保存
資料ID・版を記録。新規作成と改訂を区別する。

所定のシート・項目から抽出
固定セルは位置指定、可変行は表の範囲から抽出。AIは文章の整理を担当する。

用語を整理し、既存事例と照合
新規／重複／更新候補／矛盾ありに分ける。同じ資料・版の再取り込みを防ぐ。

担当者が元資料と候補を確認
否定表現・単位・条件の抜けを確認。元にない理由を事実として補わない。

正式なナレッジへ反映
修正済みの情報は差分を確認して更新。更新後の検索・回答への反映も確かめる。

読めない資料は保留する

様式違い、空欄、画像内の記述、図形のテキストなどを検出したら、取り込み待ちとして知らせる。

候補と正式データを分ける

未確認の抽出候補は回答根拠に混ぜない。正式データだけを参照できる保管・検索構成にする。

05
06 / 修正・追加

誤りを直し、正しかった条件は残す

起きたこと対応
抽出・要約の誤り元資料を確認して台帳を修正する。
元資料の誤り正式な手順で元資料を改訂し、台帳にも反映する。
今回だけ条件が違う元の事例を残し、別条件の事例を追加する。
事例が足りない新しい行として追加。根拠・検証状況を残す。
確認観点が足りない確認観点表に追加し、質問ルールも更新する。
管理項目が足りない列を追加し、抽出・質問・出力の設定も更新する。
修正依頼の例事例A001の影響は、常温ではなく高温時の条件です。
修正案の提示例変更対象：適用条件
修正前：記載なし
修正後：高温時（具体的な温度は未確認）
確認事項：元資料に温度範囲の記載はありますか？
修正前・修正後・理由・確認者を残して反映する。
人が補正した内容を自動取り込みで無条件に上書きしない。廃止した事例は履歴として残し、通常の根拠検索から除外する。

07 / 実現方法

生成の精度を確かめてから、自動化する

段階構成案ここで確かめること
第１段階
小さく試す		整理したExcel＋辞書＋Copilot。修正・登録は人が行う。質問が適切か、影響と根拠を拾えるか。
第２段階
継続して管理		SharePointの保管場所＋Microsoft Listsなどの管理台帳＋エージェント。更新履歴、権限、正式データの参照。
第３段階
取り込みを自動化		Power Automate、Office Scripts、Copilot Studio等を要件に応じて選定。抽出・照合・確認・書き戻し・エラー通知。

Copilotの参照・生成

Agent Builderで資料を知識源として指定する方法がある。Excelは１ブック内の１シートに整理した構成が推奨される。[1]

修正履歴・書き戻し

Listsは追加・編集とバージョン管理に対応。[2][3] 会話からの更新は別途フローを設計する。[4]

Microsoft 365 Copilotの契約だけで、すべての自動化が使えるとは限らない。管理者の許可・コネクタ・実行権限・追加ライセンスを確認する。

Agent Builderは一般知識を完全には遮断できない。[1] 指示文だけで資料由来を保証せず、事例IDと出典を検証する。台帳の更新が回答へ即時に反映されるとも仮定しない。

07
08 / 精度の確認

「書けた」より「必要な影響を拾えた」

まず代表的な20〜50件を整備する。別に取り置いた案件の変更点だけを入力し、担当者が作った期待結果と比較する。

評価項目確認する内容
見落とし必要な影響を何件拾えたか。重大な見落としは別に評価する。
無関係な候補適用条件が違う影響を、断定していないか。
根拠の正しさ事例IDが存在し、引用内容と結論が一致するか。
質問の有用性必要な条件を聞けるか。既出の情報を繰り返し聞かないか。
更新の反映修正した内容が使われ、廃止事例が根拠に出ないか。
作業時間生成だけでなく、確認・修正・登録を含めて短縮したか。
正解となる同一案件をそのまま検索できる評価だけでは、未知の変更への対応力は分からない。既知事例の検索テストと、未登録案件の検討テストを分ける。

大量の資料を指定しても全行の網羅的な照合は保証されない。漏れが残る場合は、対象部品・変更分類で候補を絞る検索処理や、必須確認項目の点検を追加する。

09 / 次に決めること

まずは共通様式１つから設計する

決まっていること

  • Microsoft 365 Copilot有償版を想定。
  • 過去資料は共通様式のExcel。
  • 基本入力は変更点。
  • 不足情報は質問して補完。
  • 辞書化、修正、追加、新資料の取り込みを行う。

これから確認すること

  • シート名と抽出対象の位置。
  • 行数の増減・結合セル・画像の有無。
  • 保存場所と資料ID・版の管理方法。
  • 取り込みと修正を確認する担当者。
  • エージェント・フローの利用可否。

最初の成果物：抽出項目の対応表、ナレッジ台帳の試作、質問・回答ルール、評価用案件。

その結果を見て、Excelのまま運用するか、Lists等へ移行するか、どこまで自動化するかを決める。

実装時に確認するMicrosoft公式資料
  1. Agent Builderへの知識源の追加 — 対応形式・参照先・制限。
  2. リスト項目の追加・編集
  3. リスト・ライブラリのバージョン管理
  4. エージェントとフローの連携

機能・制限・料金は変更されるため、実装時に会社の環境と最新情報を確認する。

GitHub Pagesに掲載するのはこの構想資料。実際の社内Excelやナレッジは会社で許可された環境に保管する。検索除外指定は設定済みだが、アクセス制限ではない。
